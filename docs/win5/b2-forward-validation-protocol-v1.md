# B2 前向き検証 事前登録案 v1（DRAFT：提案のみ。ユーザーの確認まで効力なし）

状態: **提案**。`docs/win5/b2-validation-protocol.md`（遡及評価の事前登録）は変更しない。この文書は main に入れず、PR上の提案として扱う。
ユーザーの確認なしに、採用基準を変更・確定しない。現行Bは正式表示のまま。B2は実験扱い。

## 0. 前提の整理（事実）
- 遡及評価（2025-10〜2026-10-24）の結果: 全B2候補が「人気順位に足して改善」を示せず（条件2 FAIL）、B0-refit（温度τだけ再フィット）に対する差も区間が0をまたいだ。最良候補（B2-full-b1-rating）の差は +0.007 [−0.004,+0.019]（827レース）。
- 遡及評価は「確定後の最終人気」を基準にしており、発走前の運用性能の証明ではない。
- **「10/25以降が前向き」とは限らない**: B2の予測は発走前に固定・保存されていない。10/25以降のうち、凍結（§3）より前の分は **補助的な遡及評価（retro-2）**とし、採否には使わない。前向き期間は「凍結コミット後の最初の開催日」から。

## 1. 比較する対象（事前に1つに固定）
- **主候補（採否の対象）: 1つだけ**。案: `B2-full-b1-rating`（遡及評価で最良。事後選択ではあるが、前向きデータで検証するため許容）。
- **要決定（ユーザー/GPT）**: 遡及評価で、重賞クラス（GRADED）の特徴量が一度も付かない不具合が確認された（学習期間のJRA走で GRADED 0件）。これを直した版 B2.1 を、凍結**前**に仕様として固定して主候補にするか。固定するなら、10/25以降の結果を見て調整しない。決まるまで案は現行の B2-full-b1-rating。
- 対照: **B0-refit**（温度τのみ再フィット。凍結時点で固定）。参考: B0-original（現行Bの式。τ=1/1.35）、市場確率。
- 他のB2候補（9件）は記述的に報告するだけで、**採否の対象にしない**（多重比較の回避）。

## 2. 主指標と副次条件
- **主指標**: 差 = 「B2の平均対数尤度 − B0-refitの平均対数尤度」（1レースあたり、全頭の対数尤度。正 = B2が良い）。
- **必須の副次条件（市場）**: 発走前市場確率に B2 の点数を足したとき、市場のみより対数尤度が改善する（正 = 足して改善）。
  - 市場確率: 各レースの発走10分前に最も近く、それ以前の公式単勝オッズ（`odds-snapshot`）から、逆数を正規化した確率。時刻を記録する。
  - 重みの決め方: 市場の対数確率に B2 の点数を足す対数線形（重み w は逐次推定）。月ごとに、それ以前の前向きデータだけで w を推定して、その月を評価する（初月は w=0）。最終人気は使わない。
  - 市場のスナップショットがないレースは、この副次条件の対象から外す（件数を報告）。主指標には影響しない。
- 既存protocolの条件1・2は書き換えない。上の2つは、前向き専用の別条件。

## 3. 凍結（データ収集前）
- 凍結コミットで固定: 実装コードのSHA256、候補定義、全係数とハイパーパラメータ（学習期間 2025-10-01〜凍結日の前日までを、遡及評価と同じ手順で推定）、alias辞書SHA256、B0-refit の τ、評価コード、本文書。
- 凍結後は、係数の再推定・特徴量・グリッドの変更をしない（変更するなら新しい版 v2 として、新しい前向き期間を始める）。
- 前向き期間 = 凍結コミット後の最初の開催日から。

## 4. 予測の生成と保存
- 開催日ごとの朝（8:30 JST）に、その日の全JRA平地レースの予測を Actions で生成する。
  - 入力: その時点の出馬表・取消除外・馬の履歴（**その日より前の走のみ**。取得時刻とSHA256を記録）。
  - 出力: 全頭の B0-original / B0-refit / 主候補の確率と点数のCSV、manifest（コードSHA、係数SHA、alias SHA、履歴スナップショットの時刻とSHA256、対象レース一覧、実行時刻）。
- 専用ブランチ `b2-forward` に追記のみでコミット。GitHub のコミット時刻を、発走前に生成した証拠とする。過去ファイルは書き換えない。訂正は新しいファイルで。manifest は直前の manifest のSHA256を含める（鎖）。
- 発走後に生成されたと判定できる予測（コミット時刻が発走より後）は、評価から除外し、件数を報告する。

## 5. 対象レースと除外
- 対象: JRAの平地（芝・ダート）で、出走頭数5頭以上。**障害は除外**（遡及評価のデータは `surface` が芝・ダートかで絞っていて、障害レース127件が「芝」として含まれている。前向きでは `cat` が「障害」始まりを除外する。遡及評価の結果は変更しない）。
- 除外: 同着で勝ち馬が複数、中止・競走除外などで勝ち馬が確定しない、予測が発走後。いずれも件数と理由を報告。
- 出走取消・競走除外の馬は、全モデル一律に除外して確率を再正規化する。
- 履歴がない馬は、遡及評価と同じ扱い（点数0）。欠損率・クラス不明率・履歴なし率を期間ごとに報告。

## 6. 検定と多重比較
- 区間: **開催日ごとのクラスター・ブートストラップ**（同じ日のレースは相関があるため）を主とし、レース単位は感度分析。リサンプル4000回、seed 7。
- 主指標1つのみで採否を判断。解析は3回（§7）。判定は **Z統計量**（平均差 ÷ 標準誤差）を、O'Brien-Fleming型の境界と比べる。境界は片側 α=0.025 を3回に配分した値で、3回の解析が等間隔の情報量（1/3, 2/3, 1）という前提。
  - 境界: 3.473／2.455／2.005（`scripts/forward_validation_stats.py` で、200万回のシミュレーションにより求めた。全体の第一種の誤りは 0.0251 で確認）。
  - **通常の95%区間とは別物**。k回目の「調整済み区間」は 平均差 ± z_k × 標準誤差。成功の条件は、調整済み区間の下限 > 0（= Z ≥ z_k）。通常の95%区間（±1.96×SE）の下限が0を超えても、境界に届かなければ成功ではない。
- 副次条件（市場）は主指標が基準を満たした場合のみ判定。

## 7. 必要件数・評価期間・停止規則
**計算の前提**（再現: `python scripts/forward_validation_stats.py --sigma <σ> --deff <D>`）
- Z = 平均差 ÷ (σ / √(n/D))。片側 α=0.025。σ = 1レースあたりの差（B2 − B0-refit）の標準偏差。D = デザイン効果（開催日クラスター）。
- 実測（Run #25 の保存済み予測、主候補 B2-full-b1-rating − B0-refit、`scripts/summarize_b2_validation.py` の TABLE5）:
  - 評価期間（8/1〜10/24）: 827レース、28開催日（1日あたり平均29.5レース）、**σ=0.171**、開催日ごとの級内相関 ICC=+0.004、**D=1.11**。
  - 月別の分割: σ=0.206〜0.247（F1〜F4、各8〜10開催日）。ICC は −0.014〜+0.029（D は 1.00〜1.92）。分割ごとの開催日が8〜10日と少なく、ICC の推定は不安定。
  - 日単位ブートストラップの区間は、レース単位より約15%広い（評価期間: [−0.0057,+0.0200] 対 [−0.0038,+0.0191]）。
- **σ は期間で 0.17〜0.25 とばらつく**。下の表は σ=0.17（評価期間）と σ=0.23（月別の中央付近）の2通りで示す。

**必要件数（同じ power 条件で比較。固定サンプル、片側α=0.025）**

| 検出したい改善 δ | σ=0.17, D=1.0 | σ=0.17, D=1.11 | σ=0.23, D=1.11 |
|---|---|---|---|
| power 70% | | | |
| +0.003 | 19,819 | 22,059 | 40,377 |
| +0.005 | 7,135 | 7,941 | 14,536 |
| +0.007 | 3,640 | 4,052 | 7,416 |
| +0.010 | 1,784 | 1,985 | 3,634 |
| power 80% | | | |
| +0.003 | 25,204 | 28,052 | 51,347 |
| +0.005 | 9,073 | 10,099 | 18,485 |
| +0.007 | 4,629 | 5,152 | 9,431 |
| +0.010 | 2,268 | 2,525 | 4,621 |

- 逐次解析（3回、OBF型）にすると、固定サンプルに対して必要件数が約 +1.7% 増える（シミュレーション。例: δ=0.007, power 80%, σ=0.17, D=1.0 で 4,629 → 4,707）。
- JRAの平地は1年に約3,300レース（遡及データの平地3,527レース ÷ 約12.7か月 × 12。障害は除く）。**+0.007 を power 70% で検出するには約1.2年（4,052レース）を要し、σ が大きい期間が混ざれば2年以上かかる**。+0.005 は σ=0.17 でも約2.4年（7,941レース）。
- 計算は独立レース＋正規近似に、デザイン効果 D で補正したもの。D は評価期間28日から推定した1つの値で、将来の D は不確かなため、完了時に実測の D で再評価する。

**解析時点**: 4,000レースを上限に、1,333／2,667／4,000 レース（約5／10／14か月）の3回（等間隔の情報量）。上の表の「σ=0.17, D=1.11, δ=0.007, power 70%」（約4,052）に対応。
- **成功停止**: 各回で Z が境界（3.473／2.455／2.005）以上。
- **無益停止（拘束しない）**: 2回目（2,667レース）で、設計時の対立仮説（δ=0.007）のもとでの条件付き検出力が10%未満になる Z を閾値とする。計算（`conditional_power_threshold`）: Z₂ < 0.535（平均差でおよそ +0.0019 未満、これは σ・D によらず同じ）。この規則で、対立仮説が正しい場合に早期停止する確率は約6.7%、帰無仮説（真の差が0）では約70%（シミュレーション）。検出力は 0.689（無益停止なしの 0.70 から低下）。
  - 前回案の「区間の上限が +0.003 未満」は廃止（クラスター区間・調整済み区間との整合が取れないため）。
  - 無益停止後は、前向きの新規予測の生成を止め、その時点の結果を「採用不可」として記録する。既存の予測ファイルは保存する。
- **完了**: 4,000レース（約14か月）。基準に届かなければ「採用不可」。
- **運用停止**: 予測生成の失敗や欠測が全レースの10%を超えたら、いったん止めて原因を報告。
- 解析時点以外では、効果の大きさを集計・公開しない（運用の欠測・件数だけを月次で報告）。

## 8. 採否の条件（すべて満たすこと。満たさない場合は記録して現行Bを維持）
1. 主指標が §6/§7 の境界を超える（B2 − B0-refit > 0）。
2. 副次条件（市場）が改善（95%区間の下限 > 0）。
3. 四半期ごとの3つ以上の期間で、主指標の向きが同じ。
4. 欠測・除外が §7 の運用停止の範囲内。式・取得元・時刻・SHA256 が §4 のとおり保存されている。
5. 画面の正式表示への反映は、ユーザーの確認後（暫定ルール第13項）。

## 9b. 市場オッズの取得実測（現行 `odds-snapshot`、odds-data ブランチ 2026-10-24・25）
- 対象: 10/24（36レース開催のうち収集開始 14:23 JST 以降の21レースのみ）、10/25（36レース全部）。
- 規則案（仕様）: レースごとに、**発走10分前以前（fetched_at ≤ 発走時刻 − 10分）の最新のスナップショット**を使う。発走後のスナップショット（両日とも2レースずつにあった）は使わない。締切後の最終人気は使わない。使ったスナップショットの時刻と、発走10分前との差（古さ）を必ず記録する。
- 実測（発走10分前以前の最新との差 = 古さ）:

| | 10/24 | 10/25 |
|---|---|---|
| スナップショットがあるレース | 21（全36のうち） | 36（全36） |
| 発走10分前以前の取得がある | 19／21 | 36／36 |
| 古さ ≤10分 | 5／21 | 14／36 |
| 古さ ≤20分 | 10／21 | 18／36 |
| 古さ ≤30分 | 14／21 | 22／36 |
| 古さ 中央値／最大 | 19.2分／52.7分 | 17.9分／292.9分 |

- **スケジュール実行（cron）はほとんど動いていない**: `odds-snapshot` の実行61回の内訳は、push 48、手動 6、schedule 7。10/24〜10/26 の3日間で cron の発火は 1＋約5＋3 = 7回（期待は3日×54枠=162枠で、約4%）。10/25 に36レース分が取れたのは、手動と push による実行が多かったため。
- 1回の実行は約15〜35秒（schedule の7回の実測）。HTTPリクエストは1回あたり約7〜15（ログの `page_requests`: 10/24 は16回で115、10/25 は28回で412）。保存量は2日で約0.6MB（jsonl 約0.57MB＋ログ）。
- 結論（提案にとどめる）: 現行の cron では、全レースの発走10分前（古さ ≤10分）の取得は**できない**。cron の追加ではなく、確実に起動する仕組みが要る。案: 開催日の朝に1回だけ起動し、発走時刻まで待機しながらレースごとに取得し続ける長時間ジョブ（GitHub の1ジョブは最長6時間のため、午前・午後の2ジョブ）。起動は人手またはスケジュール済みの外部トリガー。実装は未着手（指示があるまで運用は変更しない）。
